# 项目评论 @ 提及设计

## 背景

项目详情页已经有评论能力，但当前评论是孤立数据：

- 输入 `@` 时不能选择项目相关成员
- 回复只会给父评论作者发一条简单通知
- 站内消息中心、页面顶部未读数、评论页即时提醒之间没有围绕“评论提及”形成完整链路

本次需求是在项目详情页评论中补齐 `@` 提及，并让通知进入现有消息体系，而不是再做一套独立提醒。

## 目标

1. 在项目详情页评论与回复输入框内支持 `@` 项目参与成员。
2. 提及候选范围与当前“团队成员”口径一致，并扩大为：
   - 项目经理
   - 项目成员
   - 任务负责人
   - 任务参与人
3. 用户被提及时收到站内消息通知。
4. 页面顶部未读数与消息中心自动同步。
5. 用户停留在项目评论页时，可以更快看到即时弹出的提醒/气泡。

## 非目标

- 不改造为富文本编辑器
- 不引入 WebSocket 专用评论推送链路
- 不在本次改动中重做整个评论列表样式

## 方案选择

### 方案 A：前后端协同的显式提及（采用）

前端在输入 `@` 时拉取候选成员并展示下拉列表，选中后在提交时同时带上 `mentioned_user_ids`。后端按项目参与成员范围做二次校验，合法后创建评论并发送通知。

优点：

- 用户体验明确，能看到可提及对象
- 不受用户名重名、改名影响
- 后端可以严格控制允许被提及的人
- 易于复用现有消息中心与未读数逻辑

缺点：

- 需要补充前端下拉交互与候选接口

### 方案 B：仅后端解析 `@用户名`

前端保持纯文本输入，后端从评论内容中解析 `@用户名`。

优点：

- 前端改动少

缺点：

- 用户名重名和模糊匹配难处理
- 用户体验弱，无法引导正确提及
- 改名后历史内容与提及对象关系容易混乱

### 方案 C：评论专用实时推送

在方案 A 基础上，再通过 WebSocket 对评论提及做在线即时推送。

优点：

- 实时性最好

缺点：

- 需要额外维护实时链路
- 当前站内消息已存在未读轮询与提醒机制，先上重方案收益不高

## 总体设计

### 一、数据流

1. 项目详情页加载评论模块时，请求项目评论可提及成员列表。
2. 用户在主评论框或回复框输入 `@`，前端按关键字过滤成员并展示候选。
3. 用户提交评论时，前端提交：
   - `content`
   - `content_type_id`
   - `object_id`
   - `parent_id`（回复时）
   - `mentioned_user_ids`
4. 后端创建评论后：
   - 如果是回复，继续发送回复通知
   - 如果存在合法提及，发送评论提及通知
5. 通知写入 `Message` / `MessageUserRelation` 后，复用现有未读数逻辑进入消息中心。

### 二、成员口径

项目评论可提及成员范围统一收敛为一个后端帮助方法，来源包含：

- `project.manager`
- `project.members.all()`
- `project.tasks.assignee`
- `project.tasks.participants`

返回时按用户 ID 去重，并排除空值。该帮助方法同时可复用到项目详情现有“团队成员”口径，避免页面展示与评论提及出现范围不一致。

### 三、后端改动

#### 1. 项目参与成员聚合

在 `apps/project` 内补充一个聚合项目参与成员的帮助方法，供：

- 项目详情页上下文
- 评论提及候选接口
- 评论创建时合法性校验

#### 2. 评论提及候选接口

在 `CommentViewSet` 增加针对项目评论的 action，例如按 `object_id` 返回成员候选：

- `id`
- `username`
- `name`
- 展示名

该接口只返回当前用户有权限查看的项目成员候选。

#### 3. 评论创建

扩展 `CommentViewSet.create`：

- 读取 `mentioned_user_ids`
- 若评论对象不是项目，则忽略提及列表
- 若评论对象是项目，则校验提及人是否属于允许范围
- 排除评论作者自己
- 创建评论后发送提及通知

#### 4. 通知发送

回复通知与提及通知都统一走 `MessageService.send_notification(...)`。

提及通知设计：

- 分类：`comment`
- 标题：项目评论提及通知
- 关联对象：当前评论
- 跳转地址：项目详情评论锚点

这样消息中心、顶部未读数、通知偏好过滤、未读关系创建都能复用现成机制。

### 四、前端改动

在 `templates/project/detail.html` 的评论模块补充：

1. `@` 候选成员缓存与拉取
2. 主评论框和回复框的提及下拉层
3. 选中成员后在文本中插入展示名
4. 提交时带上 `mentioned_user_ids`

为降低改动风险，本次不引入第三方 mention 编辑器，直接在现有 textarea 上做轻量增强。

### 五、评论内容展示与安全

当前评论内容是直接插入 HTML 的，存在后续扩展时的 XSS 风险。本次会顺手把评论内容渲染改成安全转义，再做轻量提及高亮或纯文本展示，避免把用户输入当成 HTML 直接插入。

### 六、即时提醒

站内消息中心和顶部未读数会通过 `MessageService` 自动接入现有消息链路。

针对“评论页即时弹出提醒/气泡”，采用轻量方案：

- 在项目详情页评论模块激活时，增加比全局 60 秒更短的局部轮询
- 仅检查与当前项目评论相关的新通知或新增评论
- 一旦发现新的提及/回复消息，在评论区域弹出局部气泡提醒
- 同时调用现有未读数刷新逻辑，保证顶部角标同步

这样可以满足即时感知，又不引入专门的实时基础设施。

## 错误处理

- 非法 `mentioned_user_ids` 不应导致越权通知
- 评论为空仍按现有逻辑拦截
- 候选成员加载失败时，评论功能本身仍可继续使用，只是暂时没有 `@` 建议
- 提及通知发送失败时，应记录日志，避免影响评论主流程的可见响应

## 测试策略

按 TDD 实施，先写失败测试，再补实现。重点覆盖：

1. 项目评论候选成员范围正确且去重
2. 项目经理会进入可提及范围
3. 创建带提及的评论时，只有合法成员收到通知
4. 评论作者不会给自己发提及通知
5. 回复通知与提及通知都能正常产生
6. 站内消息未读关系被正确创建

## 影响文件

预计主要涉及：

- `apps/project/views.py`
- `apps/project/viewsets.py`
- `apps/project/serializers.py`
- `apps/project/tests.py`
- `templates/project/detail.html`

必要时会增加 `apps/project` 内的小型帮助模块，用来收敛项目成员口径与通知辅助逻辑。
