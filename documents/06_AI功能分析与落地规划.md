# DT企业智能管理系统 AI 功能分析与落地规划

> 文档位置：`documents/06_AI功能分析与落地规划.md`
> 适用对象：产品负责人、技术负责人、后端开发、前端开发、测试、实施交付、AI 功能负责人
> 文档目标：基于当前代码和业务文档，分析项目已有 AI 能力与业务入口，规划一组实用、可落地、可分阶段建设的 AI 功能。

---

## 1. 结论摘要

DT 企业智能管理系统已经具备较完整的 AI 能力雏形：模型配置、AI 聊天、知识库、RAG、意图识别、工作流、工作流执行记录、审计日志、效果反馈、A/B 测试、页面 AI 助手以及多个业务模块中的 AI 分析接口。

因此，下一阶段不建议继续单纯新增孤立 AI 页面，而应优先建设“业务页面上下文助手 + 统一 AI 服务治理 + 可复用工作流模板”的体系。

推荐第一优先级：

1. 审批与财务 AI 审核助手。
2. 合同 AI 审查助手。
3. 客户跟进与销售助手。
4. 项目风险与周报助手。
5. 库存与生产预警助手。
6. 企业知识库问答助手。

推荐第一阶段目标不是让 AI 自动替人做决定，而是让 AI 做“总结、识别风险、生成建议、预填内容、整理待办”，所有高风险动作仍由用户确认。

## 2. 当前项目理解

### 2.1 技术结构

当前项目是基于 Django 5.2 的企业管理平台，采用多应用模块化结构：

| 层级 | 当前实现 |
|---|---|
| 后端框架 | Django 5.2.1 |
| API 能力 | Django REST Framework、SimpleJWT、Session |
| 前端形态 | Django Templates + LayUI + jQuery + 静态 JS/CSS |
| 核心业务 | CRM、合同、财务、项目、任务、审批、消息、OA、个人办公、网盘、生产、库存 |
| AI 中台 | `apps.ai`、`apps.ai_orchestrator` |
| 文件与知识 | 企业网盘、Office/PDF 文档解析依赖、AI 知识库、向量表 |
| 部署依赖 | Docker、docker-compose、PostgreSQL、Redis、Gunicorn、AI Orchestrator Sidecar |

### 2.2 业务闭环

项目业务可以抽象为四条主线：

| 主线 | 业务链路 | AI 价值点 |
|---|---|---|
| 经营闭环 | 客户线索 → 客户 → 跟进 → 订单/合同 → 项目 → 财务 | 线索识别、客户画像、合同风险、回款预测、经营问答 |
| 生产库存闭环 | 产品 → BOM → 工艺 → 生产计划 → 任务 → 质检 → 入库 → 库存 | 排程建议、缺料预警、质量异常、库存预测、滞销分析 |
| 协同办公闭环 | 审批 → 消息 → 会议 → 日程 → 任务 → 个人办公 | 审批摘要、风险评估、会议纪要、待办提取、消息摘要 |
| 知识资产闭环 | 网盘/文档 → 知识库 → 向量 → RAG 问答 → 业务助手 | 制度问答、SOP 检索、项目文档问答、合同/文件摘要 |

## 4. 当前问题与机会

### 4.1 主要问题

| 问题 | 现象 | 影响 |
|---|---|---|
| AI 能力点状分散 | 各业务模块直接调用 `analysis_tools` 或 `AIClient` | 模型选择、日志、错误处理、成本统计难统一 |
| 多套模型调用层并存 | `AIClient`、`enhanced_model_service`、`AIAnalysisService`、业务分析工具并存 | 后续维护成本上升 |
| 业务 AI 结果缺少统一结构 | 有些接口返回自然语言，有些返回 dict，有些靠字符串解析 | 前端难复用，测试难覆盖 |
| 权限治理需要贯穿所有 AI 能力 | 查询服务已有权限映射，但业务 AI API 权限校验粒度不完全一致 | 可能产生越权分析或跨部门数据泄露 |
| 高风险动作需要确认机制 | 意图服务已经限制 create/update/delete，但业务场景仍需统一交互规范 | 避免 AI 直接修改关键业务数据 |
| 本地运行环境不完整 | 当前环境 `python` 不可用，Codex 自带 Python 未安装 Django | 影响测试、验证和持续交付 |

### 4.2 主要机会

| 机会 | 原因 |
|---|---|
| 前端统一助手入口已经存在 | `ai-agent-sdk.js` 可作为跨页面 AI 能力入口 |
| 业务数据模型足够丰富 | CRM、合同、财务、项目、生产、库存均已有结构化数据 |
| AI 工作流基础较完整 | 节点、连接、执行记录、权限、审计、交互均有雏形 |
| 知识库/RAG 已具备基础 | 可以将网盘、制度、SOP、项目文档转为问答能力 |
| 审批和消息是横向能力 | AI 结果可以天然转化为审批建议、消息提醒和待办 |

## 5. 三种落地路线

### 5.1 路线 A：继续按模块增加 AI 功能

做法：每个业务模块单独新增 AI 按钮、接口、提示词和返回格式。

优点：

- 开发快，局部改动小。
- 适合快速演示单点功能。

缺点：

- 容易形成新孤岛。
- 模型调用、日志、成本、权限难统一。
- 后续维护压力大。

适用场景：临时演示或某个模块极度紧急。

### 5.2 路线 B：先建设 AI 中台治理，再逐步接业务

做法：先统一 AI 调用层、日志、权限、反馈、结构化输出，再接入业务模块。

优点：

- 架构稳，后续扩展成本低。
- 有利于审计、安全、成本控制。

缺点：

- 第一阶段业务可见价值慢。
- 容易陷入平台建设过度。

适用场景：团队资源充足、希望长期产品化。

### 5.3 路线 C：业务助手先行，平台治理同步收敛

做法：优先选择 3-5 个高频业务场景做上下文助手，同时抽出统一 AI 调用、日志、权限、反馈规范。

优点：

- 业务可见价值快。
- 不牺牲长期架构。
- 可以边上线边沉淀通用能力。

缺点：

- 需要产品和技术负责人控制边界。
- 每个 AI 功能必须遵守统一输出和权限规范。

推荐：选择路线 C。

## 5.4 当前已落地的 AI 写操作治理

截至 2026-06-30，项目已在 `apps.ai` 内补齐一套统一的业务写操作执行框架，用于承接自然语言识别后的确认、执行和回退。

已实现的关键约束：

- 写操作必须先生成预览，再由用户确认。
- 确认后才允许执行真实写入、删除或审批动作。
- 执行结果会落库为 `AIOperation`、`AIOperationChangeSet`、`AIOperationConfirmation`、`AIOperationRollback`。
- 回退按单次操作的变更集逆序执行，不做全库回滚。
- 删除类操作支持按快照重建单条记录，适配财务这类硬删场景。
- 财务写操作已接入权限检查，执行前会再次校验当前用户是否拥有对应业务权限。

当前首批接入模块：

- 客户
- 审批
- 项目
- 财务报销 / 发票申请
- 企业网盘文件、文件夹、分享与权限设置

其中财务写操作已经明确区分为“预览 -> 确认 -> 执行 -> 单条回退”链路，删除类变更支持按快照重建单条记录。
企业网盘写操作已补齐分享创建/更新/删除、权限公开状态切换、用户与部门共享关系调整，并保持同样的预览、确认、执行、回退边界；回退仅针对单次操作的变更集，不影响其他分享或权限记录。

## 6. 推荐 AI 功能清单

### 6.1 P0：应优先落地

#### 6.1.1 审批与财务 AI 审核助手

目标用户：审批人、财务人员、管理者。

核心能力：

- 自动总结审批单/报销单关键信息。
- 标记异常金额、异常时间、缺少附件、重复报销、超预算风险。
- 展示相似历史审批或报销记录。
- 生成“同意/驳回/补充材料”的建议意见草稿。

落地方式：

- 复用 `apps/approval/ai_views.py`、`apps/finance/ai_views.py`。
- 统一输出结构：`risk_level`、`summary`、`risk_points`、`suggestion`、`recommended_action`、`confidence`。
- 前端接入审批详情页、报销详情页。
- 对于 AI 直接发起的数据写入类操作，先走预览与确认，再进入统一执行网关。
- 回退必须按单条操作恢复，不影响其他历史记录。

边界：

- AI 只给建议，不自动审批。
- 审批动作必须由人点击确认。

验收指标：

- 审批人能在详情页看到 AI 摘要和风险点。
- 高风险项必须展示原因。
- 用户可以复制或一键填入审批意见。

#### 6.1.2 合同 AI 审查助手

目标用户：销售、法务、合同管理员、管理者。

核心能力：

- 合同摘要。
- 关键条款提取：金额、付款节点、交付节点、违约责任、终止条件、有效期。
- 风险点识别：缺少付款条件、违约责任不清、交付时间不明确、金额异常。
- 履约提醒建议。

落地方式：

- 复用 `apps/contract/ai_views.py` 和合同模型已有 `ai_risk_level`、`ai_risk_points`、`ai_key_terms` 字段。
- 合同详情页增加 AI 审查面板。
- 结果保存到合同模型，避免重复调用。

边界：

- 不输出法律结论，只输出“业务风险提示”。
- 高风险结果需要用户确认后写入合同记录。

验收指标：

- 合同详情能一键生成摘要和风险点。
- 已生成结果能缓存复用。
- 修改合同后允许重新分析。

#### 6.1.3 客户跟进与销售助手

目标用户：销售、客户经理、销售主管。

核心能力：

- 客户画像：行业、等级、来源、历史跟进、订单/合同情况。
- 下一步跟进建议。
- 跟进记录润色。
- 根据通话/拜访记录提取客户意向。
- 生成销售话术或邮件/消息草稿。

落地方式：

- 复用 `CustomerAnalysisTool`、客户 AI 机器人、`ai-agent-sdk.js` 文本润色入口。
- 客户详情页和跟进记录表单接入上下文助手。

边界：

- 客户创建、修改仍走业务表单。
- AI 可以预填表单，但必须由用户保存。

验收指标：

- 销售在客户详情页能生成客户摘要。
- 跟进表单能一键润色或生成下一步计划。
- AI 结果不越权读取其他销售客户。

#### 6.1.4 企业知识库问答助手

目标用户：全员、实施、客服、行政、人事、生产人员。

核心能力：

- 查询制度、流程、SOP、操作手册、项目文档。
- 基于知识库给出答案和来源条目。
- 不知道时明确提示未找到，不编造。
- 与网盘文件摘要和标签联动。

落地方式：

- 复用 `AIKnowledgeBase`、`AIKnowledgeItem`、`AIKnowledgeVector`、`EnhancedRAGService`。
- 增强知识库条目的来源字段、权限过滤和引用展示。
- 在 AI 聊天中优先判断知识库意图。

边界：

- 必须按用户权限过滤知识库和网盘文件。
- 对答案附上来源，降低幻觉风险。

验收指标：

- 用户能问“报销流程怎么走”“某个 SOP 如何执行”。
- 返回答案包含来源标题。
- 无权限文档不会出现在答案中。

### 6.2 P1：第二阶段落地

#### 6.2.1 项目风险与周报助手

- 缺料预警。

### 6.3 P2：第三阶段落地

#### 6.3.1 经营驾驶舱 AI 分析

能力：

- 对客户、合同、项目、财务、生产、库存做跨模块经营总结。
- 自动解释仪表盘波动。
- 生成管理层日报/周报/月报。

前置条件：

- 指标口径稳定。
- 跨模块数据权限明确。
- AI 调用日志和成本统计完善。

#### 6.3.2 AI 工作流模板市场

能力：

- 内置合同审查、报销审核、库存预警、项目周报、会议待办等模板。
- 支持管理员复制、编辑、发布、授权。
- 支持执行记录、失败重试、人工确认。

前置条件：

- 工作流权限、版本、审计、调试能力稳定。
- 节点配置 Schema 足够清晰。

#### 6.3.3 AI 质量评估与 A/B 测试

能力：

- 同一业务场景对比不同模型或提示词。
- 收集用户评分。
- 统计准确率、采纳率、平均耗时、调用成本。

复用入口：

- `AIFeedback`、`AIBatchTest`、`AIBatchTestVariant`、`AIBatchTestResult`。

## 7. 推荐架构原则

### 7.1 统一 AI 调用门面

建议新增或收敛为一个统一服务，例如：

```text
apps/ai/services/ai_gateway.py
```

职责：

- 根据任务类型选择模型配置。
- 封装 chat、embedding、summary、classification、extraction。
- 统一超时、重试、错误提示。
- 记录 `AILog`、token、耗时、模型、业务上下文。
- 提供结构化输出校验。

### 7.2 统一业务 AI 输出协议

建议所有业务 AI 接口都返回：

```json
{
  "code": 0,
  "msg": "success",
  "data": {
```

### 7.3 所有高风险动作必须人工确认

高风险动作包括：

- 新增、修改、删除业务数据。
- 审批通过、驳回、撤回。
- 合同作废、终止、归档。
- 财务打款、发票作废。
- 库存出入库、调拨、盘点确认。
- 生产计划发布、任务关闭。

AI 可以：

- 生成草稿。
- 预填表单。
- 给出建议。
- 解释原因。

AI 不应直接：

- 绕过页面权限修改数据。
- 直接审批或付款。
- 直接删除业务记录。

### 7.4 权限先于检索和生成

所有 AI 功能必须遵守：

1. 先判断用户是否有业务对象访问权限。
2. 再取业务上下文。
3. 再调用模型。
4. 输出结果只能包含用户有权看到的数据。
5. 记录 AI 调用日志。

### 7.5 先业务页面，后独立 AI 页面

优先在用户已经工作的页面嵌入 AI：

- 审批详情页。
- 报销详情页。
- 合同详情页。
- 客户详情页。
- 项目详情页。
- 库存详情页。
- 生产计划详情页。
- 网盘文件详情页。

独立 AI 聊天适合作为全局入口，但不应成为唯一入口。

## 11. 风险与治理建议

| 风险 | 建议 |
|---|---|
| AI 幻觉 | 输出必须包含依据或来源；无法确认时提示“不确定” |
| 数据越权 | 先权限过滤，再检索和生成 |
| 自动化误操作 | 高风险动作只生成草稿和建议，不直接执行 |
| 成本不可控 | 记录调用量、缓存分析结果、限制超长输入 |
| 多模型接口混乱 | 收敛到统一 AI 调用门面 |
| Prompt 难维护 | 按任务类型集中管理提示词和结构化输出 Schema |
| 结果不可评估 | 接入反馈、A/B 测试和场景级指标 |
| 本地环境不可验证 | 先恢复 Python/Django 环境，再进入功能实施 |

### 16.3 权限与安全边界

- 查询仍先检查业务权限映射，再执行具体查询处理器。
- 新增、修改、删除、审批动作、网盘分享/权限变更仍必须进入确认链路，不允许 AI 直接写库。
- 已保持“单次操作 change_set 回退”原则，回退只影响该次操作涉及的对象，不做全库或批量无差别回滚。
- 对尚未接入完整业务权限节点的写操作入口，增强意图服务会返回不可直接执行的业务交接结果，避免 AI 绕过页面权限。
