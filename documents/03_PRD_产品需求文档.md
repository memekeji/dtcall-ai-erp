# DT企业智能管理系统 PRD 产品需求文档

> 产品名称：DT 企业智能管理系统
> 产品类型：企业级数字化经营管理平台 / 综合 ERP+CRM+OA+MES+AI 平台
> 适用范围：企业内部管理、业务经营、协同办公、生产制造、库存供应链、智能辅助决策
> 文档目标：让产品、研发、测试、实施、运维和业务方清晰理解系统目标、用户角色、业务场景、功能范围、非功能要求和验收标准。

---

## 1. 产品背景

企业在日常经营中通常面临以下问题：

1. 客户信息、销售跟进、合同、项目、财务数据分散在不同工具中，无法形成统一业务闭环。
2. 组织、员工、岗位、权限、菜单配置缺少统一管理，导致系统扩展难、权限控制难。
3. 行政办公、审批、消息、日程、会议、个人工作记录分散，协同效率低。
4. 生产制造企业中产品、BOM、工艺、设备、生产计划、质检、完工、库存之间存在断点。
5. 企业网盘、附件、文档、合同、项目资料缺少统一权限管理和共享机制。
6. AI 能力如果独立建设，容易成为孤岛，无法真正融入客户、合同、项目、生产、库存等业务流程。
7. 系统运维、备份、服务配置、云存储配置、日志审计缺少统一入口。

DT 企业智能管理系统的定位是：以 Django 后台为统一入口，将企业经营、协同办公、生产制造、库存供应链和 AI 智能能力整合到一套可部署、可扩展、可权限控制、可持续演进的企业管理平台中。

## 2. 产品定位

### 2.1 产品愿景

构建一套覆盖企业经营全流程的智能化管理系统，使企业能够在一个统一后台中完成从客户线索到合同签署、项目交付、财务收付、生产制造、库存流转、协同办公和智能分析的闭环管理。

### 2.2 产品价值

| 价值方向 | 说明 |
|---|---|
| 统一管理 | 将用户、组织、权限、业务、生产、库存、财务、办公、AI 统一到一个平台 |
| 降低数据孤岛 | 客户、合同、项目、财务、生产、库存之间建立可追踪关联 |
| 提升协同效率 | 通过审批、消息、任务、OA、个人办公提高跨部门协作效率 |
| 强化生产管控 | 将产品、BOM、工艺、设备、计划、任务、质检、完工入库串联起来 |
| 增强数据智能 | 通过 AI 工作流、知识库、RAG、业务 AI 分析提升辅助决策能力 |
| 降低运维成本 | 统一系统配置、备份、日志、存储和服务配置入口 |
| 提高安全性 | 通过认证、角色、菜单权限、数据权限和审计日志控制系统风险 |

### 2.3 产品边界

系统当前定位为企业内部综合管理平台，不直接定位为以下产品：

1. 面向公众用户的开放电商平台。
2. 独立的移动 App 工程。
3. 完全前后端分离的 SaaS 平台。
4. 独立大模型训练平台。
5. 专业 SCADA 系统或工业控制实时系统。

系统可与上述能力集成，但核心仍是企业后台管理和业务流程闭环。

### 3.2 权限要求

1. 用户必须登录后才能访问后台业务页面。
2. 菜单展示应根据用户角色和权限过滤。
3. 页面访问必须校验菜单或页面权限。
4. 数据查询必须符合数据权限范围。
5. 管理员可配置用户、角色、菜单、组织和系统参数。
6. 普通用户只能访问授权菜单和授权数据。
7. 涉及财务、合同、审批、AI、系统配置、备份、存储的功能必须严格控制访问权限。

## 4. 核心业务目标

### 4.1 经营闭环目标

系统应支持以下业务闭环：

```text
客户线索 → 客户管理 → 联系人 → 跟进记录 → 客户意向 → 客户订单 → 客户合同 → 项目交付 → 财务收付 → 数据统计
```

目标：让企业从销售线索到履约回款的全过程有统一记录、统一责任人和统一统计口径。

### 4.2 生产库存闭环目标

系统应支持以下生产链路：

```text
产品资料 → BOM → 工艺路线 → 生产计划 → 生产任务 → 质检 → 完工报告 → 产品入库 → 库存流转 → 预警报表
```

目标：让生产制造过程从基础资料到计划执行、质量控制、入库出库都有可追踪记录。

### 4.3 协同办公目标

系统应支持：

- 审批流程。
- 消息通知。
- 日程会议。
- 个人任务。
- 工作记录和汇报。
- 企业网盘共享。
- 行政办公。

目标：减少跨部门沟通成本，提高业务流转效率。

### 4.4 AI 智能目标

系统应支持：

- AI 模型配置。
- AI 工作流设计与执行。
- 知识库与向量检索。
- 聊天与业务问答。
- 合同、财务、项目、任务、审批、网盘、生产、库存等业务 AI 能力。

目标：将 AI 从单独聊天工具升级为嵌入业务流程的智能辅助能力。

## 6. 详细功能需求

## 6.1 登录认证与用户权限

### 6.1.1 登录认证

#### 功能说明

用户通过登录页输入账号、密码和验证码进入系统。系统认证通过后建立 Session，并根据角色和权限展示菜单。

#### 需求点

| 编号 | 需求 |
|---|---|
| AUTH-001 | 系统必须提供登录页面 |
| AUTH-002 | 登录必须校验用户名、密码和验证码 |
| AUTH-003 | 登录成功后进入后台主框架 |
| AUTH-004 | 登录失败应给出明确错误提示 |
| AUTH-005 | 用户可安全登出系统 |
| AUTH-006 | 登出后应清理本地标签页缓存和会话状态 |
| AUTH-007 | API 可通过 JWT 获取、刷新和验证 Token |

#### 验收标准

1. 未登录访问受保护页面时，应跳转登录或拒绝访问。
2. 错误验证码不能登录。
3. 错误账号或密码不能登录。
4. 登录后左侧菜单按权限展示。
5. 登出后再次访问后台页面需要重新登录。

### 6.1.2 用户、员工与人事

#### 功能说明

系统应统一管理员账号和员工主体，支持员工资料、人事档案、调岗、离职、奖惩、关怀和员工合同管理。

#### 需求点

| 编号 | 需求 |
|---|---|
| USER-001 | 支持员工列表查看、筛选、搜索 |
| USER-002 | 支持员工新增、编辑、删除或禁用 |
| USER-003 | 支持员工档案维护 |
| USER-004 | 支持员工调岗记录 |
| USER-005 | 支持员工离职记录 |
| USER-006 | 支持奖惩记录 |
| USER-007 | 支持员工关怀记录 |
| USER-008 | 支持员工合同记录 |
| USER-009 | 支持主部门和次要部门关系 |
| USER-010 | 员工应可关联角色、权限和部门 |

#### 验收标准

1. 员工账号可用于登录。
2. 员工数据可作为负责人、审批人、项目成员、消息接收人等被业务模块引用。
3. 禁用或离职员工不应继续拥有正常业务访问权限。

### 6.1.3 角色、权限和菜单

#### 功能说明

管理员可维护角色、权限、菜单和部门角色关系。系统根据权限生成可见菜单，并在页面访问时进行校验。

#### 需求点

| 编号 | 需求 |
|---|---|
| PERM-001 | 支持角色列表、创建、编辑、删除 |
| PERM-002 | 支持为角色分配权限 |
| PERM-003 | 支持菜单树维护 |
| PERM-004 | 支持菜单图标、路径、排序、父子关系 |
| PERM-005 | 支持根据用户角色过滤菜单 |
| PERM-006 | 支持部门与角色关系配置 |
| PERM-007 | 支持数据权限控制 |

#### 验收标准

1. 用户只能看到有权限的菜单。
2. 用户直接访问无权限 URL 时应被拒绝。
3. 数据权限不满足时，不应返回越权数据。

| NFR-MAINT-005 | 跨应用交互应通过已定义接口或公共服务 |
| NFR-MAINT-006 | 禁止产生重复模型、重复功能和功能孤岛 |
| NFR-MAINT-007 | 代码应遵循项目现有风格和 Django 规范 |
| NFR-MAINT-008 | 重要架构变更应同步更新文档 |

### 7.5 部署与运维需求

| 编号 | 需求 |
|---|---|
| NFR-OPS-001 | 支持本地 Django runserver 启动 |
| NFR-OPS-002 | 支持 Docker 镜像构建 |
| NFR-OPS-003 | 支持 docker-compose 编排 PostgreSQL、Redis、Web、AI Orchestrator |
| NFR-OPS-004 | 容器启动应自动执行数据库迁移 |
| NFR-OPS-005 | 容器启动应执行静态文件收集 |
| NFR-OPS-006 | 生产应使用 Gunicorn 或等效 WSGI 服务 |
| NFR-OPS-007 | 数据库、media、云存储配置应纳入备份方案 |
| NFR-OPS-008 | 应支持日志查看和问题排查 |

## 8. 页面与交互需求

### 8.1 后台主框架

| 元素 | 要求 |
|---|---|
| 顶部栏 | 展示系统 Logo、用户信息、消息入口、用户菜单 |
| 左侧菜单 | 从数据库菜单加载，支持多级菜单 |
| 主工作区 | LayUI Tab + iframe |
| 标签页 | 支持新增、切换、关闭、持久化恢复 |
| 弹窗 | 新增、编辑、详情页面优先右侧 80% 弹出 |
| AI 数字人 | 作为主框架辅助入口存在 |

### 8.2 列表页面

1. 应有搜索或筛选区域。
2. 应有数据表格。
3. 应有新增、编辑、删除、详情等操作入口。
4. 应支持分页。
5. 危险操作应二次确认。
6. 操作成功或失败应有反馈。

### 8.3 表单页面

1. 应使用 LayUI 表单风格。
2. 必填项应明确标识。
3. 提交前应进行前端基础校验和后端最终校验。
4. 保存成功后应关闭弹层并刷新父级列表。
5. 保存失败应保留用户已输入内容并显示错误。

### 8.4 详情页面

1. 应展示主记录信息。
2. 应展示关联记录，如客户联系人、跟进、订单、合同等。
3. 应提供必要的业务操作入口。
4. 应遵循右侧弹层或 iframe 子页规范。

## 9. 数据权限与审计需求

### 9.1 数据权限

数据权限应至少支持以下维度：

1. 本人数据。
2. 本部门数据。
3. 下级部门数据。
4. 指定角色数据。
5. 指定用户数据。
6. 全部数据。

适用模块包括但不限于：

- 客户。
- 合同。
- 项目。
- 财务。
- 任务。
- 网盘。
- 生产。
- 库存。
- AI 工作流。

### 9.2 审计日志

关键操作应记录：

1. 操作人。
2. 操作时间。
3. 操作模块。
4. 操作对象。
5. 操作类型。
6. 操作结果。
7. IP 或请求上下文。

重点审计操作包括：

- 登录失败和登录成功。
- 用户、角色、权限变更。
- 财务数据变更。
- 合同终止、作废、归档。
- 审批处理。
- 文件分享和下载。
- 存储配置和服务配置变更。
- AI 模型配置变更。

## 11. 验收总标准

### 11.1 项目级验收

1. 系统可正常启动并进入登录页。
2. 登录、登出、验证码、菜单权限正常。
3. 后台主框架正常展示顶部栏、左侧菜单、Tab 工作区。
4. 已挂载业务模块可通过菜单或路由访问。
5. 客户、合同、项目、财务链路可形成闭环。
6. 产品、BOM、工艺、生产计划、生产任务、质检、完工、库存链路可形成闭环。
7. 审批、消息、网盘、OA、个人办公可作为横向协同能力使用。
8. AI 模块可配置模型、工作流、知识库并被业务模块调用。
9. 系统配置、日志、备份、存储配置有管理入口。
10. 权限不足用户无法访问越权页面和数据。

### 11.2 文档级验收

1. 架构图能一眼理解系统整体结构。
2. PRD 能覆盖主要角色、模块、需求和验收标准。
3. 业务模块说明能明确每个应用的职责边界和核心模型。
4. 运维文档能说明部署、环境变量、安全和备份要点。
5. 文档不包含敏感密钥、模拟数据或无关垃圾内容。

## 12. 风险与待确认事项

| 风险/待确认项 | 说明 | 建议 |
|---|---|---|
| 部门模型并存 | `apps.department.Department` 与 `apps.user.models.Department` 并存 | 明确主部门模型，新增功能优先使用 `apps.department.Department` |
| 任务模型并存 | `apps.project.Task` 与 `apps.task.Task` 并存 | 明确项目任务与独立任务边界 |
| 审批模型并存 | `apps.approval` 与 `apps.oa` 均有审批模型 | 明确通用审批和 OA 审批边界 |
| 库存入口 | `inventory` 已注册且有路由，但主路由未直接挂载 | 上线前确认是否补充 `/inventory/` 入口 |
| AI 权限 | AI 横向访问多个业务模块 | 必须接入数据权限和日志审计 |
| 前端风格 | 部分页面可能存在独立样式或外部 CDN | 后续逐步统一到项目本地资源与 LayUI 风格 |
| 实时能力 | 依赖 channels，但 ASGI/Channel Layer 配置需进一步核验 | 若启用 WebSocket 实时监控，应完善配置 |

## 13. 迭代建议

### 13.1 第一优先级

1. 明确部门模型、任务模型、审批模型边界。
2. 补齐库存入口策略。
3. 梳理菜单权限和数据权限规则。
4. 统一新增、编辑、详情页右侧 80% 弹出规范。
5. 强化系统配置、存储配置、AI 配置的敏感信息保护。

### 13.2 第二优先级

1. 完善客户、合同、项目、财务之间的流转体验。
2. 完善生产到库存的业务闭环。
3. 增强消息和审批的跨模块联动。
4. 完善 AI 工作流和知识库在业务页面中的落地入口。
5. 优化首页仪表盘和经营统计。

### 13.3 第三优先级

1. 建立统一的数据字典和接口文档。
2. 建立完整的权限矩阵。
3. 建立标准测试用例库。
4. 建立运维监控、告警、备份恢复演练流程。
5. 推进历史模型和旧路径治理。

## 14. 结论

DT 企业智能管理系统的产品核心不是单个模块，而是企业经营管理闭环。系统已经具备较完整的业务覆盖面和横向平台能力，后续产品规划应围绕以下原则推进：

1. 以统一用户、组织、权限为基础。
2. 以客户、合同、项目、财务为经营主链路。
3. 以产品、生产、库存为制造供应链主链路。
4. 以审批、消息、OA、网盘为协同支撑。
5. 以 AI 工作流、知识库和业务 AI 入口作为智能化增强。
6. 以统一前端风格、安全配置、审计日志和运维部署保障系统长期可维护。
