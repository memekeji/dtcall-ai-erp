# DT企业智能管理系统文档导航与项目速览

> 文档位置：`.trae/documents`
> 适用对象：产品负责人、项目经理、后端开发、前端开发、测试、运维、实施交付、企业管理者
> 文档目标：通过一个入口快速理解 DT 企业智能管理系统的业务定位、技术架构、模块边界、核心数据链路、部署方式和后续开发注意事项。

---

## 1. 一句话理解项目

DT 企业智能管理系统是一个基于 Django 5.2 的企业级数字化管理平台，采用多应用模块化架构，将用户权限、组织架构、客户 CRM、合同、财务、项目、任务、审批、消息、OA、个人办公、企业网盘、生产 MES、库存进销存、AI 工作流与知识库等能力整合在同一套后台系统中，为企业提供从业务线索、成交履约、项目交付、生产制造、库存流转到财务结算和智能化分析的闭环管理能力。

## 3. 项目关键结论

### 3.1 技术栈结论

| 层级 | 当前实现 |
|---|---|
| 后端框架 | Django 5.2.1 |
| API 框架 | Django REST Framework 3.15.2 |
| 认证方式 | 自定义 `Admin` 用户模型、Session、SimpleJWT、验证码 |
| 权限机制 | 自定义认证后端、菜单权限中间件、数据权限中间件、Django Group/Permission 扩展 |
| 数据库 | PostgreSQL 优先，未配置数据库环境变量时使用 SQLite 兜底，依赖中包含 PyMySQL |
| 缓存与会话 | Redis 优先，未配置 Redis 时使用本地内存缓存；Session 使用 cache backend |
| 前端方式 | Django Templates + LayUI + jQuery + 静态 CSS/JS；没有独立 Node/Vite 前端工程 |
| 页面承载 | 后台主框架使用 LayUI Tab + iframe 工作区 |
| 文件处理 | Office、PDF、图片、Excel、PPT、文档预览与解析能力 |
| 云存储 | OSS、COS、OBS、BOS、七牛、S3、WebDAV |
| 工业采集 | MQTT、Modbus 等协议依赖，生产模块已有数据采集服务 |
| AI 能力 | AI 模型配置、工作流、知识库、RAG、意图识别、聊天、业务 AI 视图 |
| 部署方式 | Docker、docker-compose、Gunicorn、PostgreSQL、Redis、AI Orchestrator Sidecar |

### 3.3 业务链路结论

```text
用户与组织
  ↓
权限、菜单、部门、岗位、员工档案
  ↓
客户 CRM → 合同/订单 → 项目交付 → 财务收付款
             ↓
          产品/供应商
             ↓
       生产计划/BOM/工艺/设备
             ↓
       生产任务/质检/完工/数据采集
             ↓
       库存入库/出库/调拨/盘点/预警

横向支撑：审批、消息、OA、个人办公、企业网盘、AI、系统配置、日志、备份、云存储
```

## 4. 系统最重要的五个核心对象

| 核心对象 | 所属模块 | 为什么重要 |
|---|---|---|
| `user.Admin` | `apps.user` | 全项目身份中心，负责人、创建人、审批人、消息接收人、文件拥有者、AI 工作流拥有者都围绕它建立关系 |
| `department.Department` | `apps.department` | 多数业务模块的组织维度核心，用于部门负责人、项目归属、生产部门、文件共享、公告目标部门等 |
| `customer.Customer` | `apps.customer` | 业务线索与交易起点，可关联联系人、跟进、订单、客户合同、客户发票，并流转到项目和财务 |
| `contract.Product` | `apps.contract` | 产品基础数据，向生产 BOM、工艺路线、生产计划提供产品来源 |
| `ai.AIModelConfig` / `ai.AIWorkflow` | `apps.ai` | AI 能力入口，用于模型配置、工作流编排、业务智能分析、知识库和 RAG |

## 5. 模块分层速览

| 层级 | 模块 | 职责 |
|---|---|---|
| 访问层 | `templates`、`static`、LayUI、jQuery、iframe Tab | 页面展示、菜单导航、表格、表单、弹窗、标签页工作区 |
| 路由层 | `dtcall/urls.py`、各 `apps/*/urls.py` | URL 分发、旧路径兼容重定向、业务入口挂载 |
| 视图层 | 各 `apps/*/views.py`、`views/` 子包、`ai_views.py` | 页面渲染、表单处理、接口响应、业务入口编排 |
| 服务层 | `apps/*/services.py`、`apps/*/services/` | 业务服务、AI 服务、生产采集、调度、消息通知、存储服务 |
| 模型层 | 各 `apps/*/models.py`、`apps/user/models/` | ORM 模型、业务实体、字段约束、跨应用外键与多对多关系 |
| 基础设施层 | PostgreSQL、Redis、Media、Static、云存储、Docker、Gunicorn | 数据持久化、缓存、会话、文件、部署运行 |

## 6. 当前代码中的重要边界提醒

这些不是立即要求修改的问题，而是在后续开发、需求设计和数据治理中必须注意的边界。

| 边界点 | 当前情况 | 后续建议 |
|---|---|---|
| 部门模型并存 | `apps.department.Department` 与 `apps.user.models.Department` 同时存在 | 新增组织架构能力前必须确认主模型，优先使用当前多数业务引用的 `apps.department.Department` |
| 任务模型并存 | `apps.project.Task` 与 `apps.task.Task` 同时存在 | 项目内任务走 `project`，独立协同任务走 `task`，不要混用 |
| 审批模型并存 | `apps.approval` 和 `apps.oa` 均有审批相关模型 | 通用审批能力建议走 `approval`，OA 内部审批需明确是否继续保留或迁移 |
| 企业模型并存 | `enterprise.Enterprise` 与未注册的 `public.Enterprise` 同名 | 新功能不要直接依赖 `public.Enterprise`，除非确认该模块恢复启用 |
| 库存路由 | `inventory` 已安装且有完整路由，但主路由未挂载 `/inventory/` | 如需访问库存页面，需要补充根路由挂载或确认菜单是否通过其他路径进入 |
| AI 编排路由 | `ai_orchestrator` 已安装，有后台命令，但未发现根路由挂载 | 如果仅作为 Sidecar 后台进程无需页面入口；如果提供管理页面/API，需要单独设计 |
| 旧路径兼容 | `dtcall/urls.py` 存在大量 `/adm/`、`/basedata/`、`/oa/*` 兼容重定向 | 路由改造时必须保留历史菜单与外部链接兼容性 |
| 前端资源方式 | 当前是 Django 模板 + 静态资源，不是独立前端工程 | 新页面应遵循 LayUI、统一模板、右侧 80% 弹层规范，不应随意引入新的前端工程体系 |

## 7. 适合不同角色的快速阅读建议

### 7.1 产品负责人

建议重点阅读：

1. `03_PRD_产品需求文档.md`
2. `02_架构图合集.md` 中的业务链路图、模块能力地图
3. `04_业务模块与数据模型说明.md` 中的模块职责表

重点关注：

- 产品目标是否覆盖企业管理全流程。
- CRM、合同、项目、财务、生产、库存是否形成闭环。
- AI 能力目前是横向能力，不应作为孤立模块设计。
- 审批、消息、权限是所有业务模块都要复用的平台能力。

### 7.2 后端开发

建议重点阅读：

1. `01_系统架构设计说明.md`
2. `04_业务模块与数据模型说明.md`
3. `05_部署运行与运维安全说明.md`

重点关注：

- `user.Admin` 是全局用户模型。
- 业务模型跨应用关联较多，新增模型前必须先查已有模型。
- 系统使用自定义中间件进行权限和数据权限控制。
- 不要在 `apps` 内新增模板目录，模板统一放在根目录 `templates`。
- 不要在业务模块中直接复制已有能力，应通过公共服务或已有模块边界集成。

### 7.3 前端开发

建议重点阅读：

1. `01_系统架构设计说明.md` 的前端架构章节
2. `02_架构图合集.md` 的前端页面结构图
3. `03_PRD_产品需求文档.md` 的交互与体验需求

重点关注：

- 后台主框架是 LayUI Tab + iframe。
- 二级/详情/新增/编辑页面应优先使用右侧弹出 80% 工作区方式。
- 页面风格必须延续 LayUI、`common.css`、已有业务页面样式。
- 不应创建与项目风格孤立的新 UI 体系。

### 7.4 测试与实施

建议重点阅读：

1. `03_PRD_产品需求文档.md` 的验收标准
2. `04_业务模块与数据模型说明.md` 的业务链路
3. `02_架构图合集.md` 的业务链路图和权限流程图

重点关注：

- 用户登录、菜单权限、数据权限是否按角色生效。
- 客户到合同、项目、财务的链路是否完整。
- 生产与库存链路是否能从产品、BOM、计划、任务、完工流转到库存。
- 文件上传、预览、分享、权限是否符合企业网盘场景。
- 消息、审批、AI 分析应验证与业务上下文的联动。

### 7.5 运维与交付

建议重点阅读：

1. `05_部署运行与运维安全说明.md`
2. `01_系统架构设计说明.md` 的部署架构章节
3. `02_架构图合集.md` 的部署拓扑图

重点关注：

- 生产建议 PostgreSQL + Redis + Gunicorn + 反向代理。
- `DJANGO_SECRET_KEY`、数据库密码、Redis 密码、AI API Key 等必须通过环境变量或系统配置管理，不得硬编码。
- `media`、数据库、Redis 数据目录需要纳入备份策略。
- `DEBUG` 生产必须关闭。
